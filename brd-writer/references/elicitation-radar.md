# 逼問技巧（Elicitation Radar）

給 `SKILL.md` 引用的技巧細節。訪談時隨時套用，不分 Step——聽到任何一個紅旗語言模式，當下就要停下來多問一句，不要等到走到「對應的 Step」才想起來。

## 兩種追問姿態，不要用錯

- **目標精確度（挑戰姿態）**——需求方對自己的目標通常只有「大概的方向」，這裡要像資深 BA 一樣**質疑、逼精確**：「這樣夠具體嗎？」「這個詞是什麼意思？」把模糊的目標逼成有公式、有分子分母的 Goal Metric。用在 Step 3（需求方與商業目標）。
- **現況/SOP 萃取（引導姿態）**——需求方對自己每天在做的事其實很熟，只是沒有文件化的習慣，知識是內隱的，不是不知道。這裡不是質疑，是**順著他的敘述一步步引導回憶**：「然後呢？」「那個時候你看到什麼畫面？」把內隱知識問成看得懂的文字。用在 Step 2（現況與痛點）。

搞反了會很卡：對目標用萃取姿態，會問不出精確度；對 SOP 用挑戰姿態，會讓對方覺得被質疑「你連自己在做什麼都講不清楚」，反而防衛起來。

## 紅旗語言雷達（貫穿全程，隨時觸發）

下表不是只在特定 Step 才查——整場訪談，聽到任何一種模式，當場追問，不限於表列的字眼。

| 紅旗模式 | 例子 | 追問方向 |
|---|---|---|
| 抽象動詞 | 「處理」「跟進」「關心」 | 具體做了什麼動作？看了什麼畫面、輸入了什麼？ |
| 未定義專有名詞/縮寫 | 「CHA」「用 XX 系統」 | 這是什麼？做什麼用的？公司內部還有誰知道這個？ |
| 被動/無主詞語句 | 「會被發送提醒」「資料會更新」 | 誰做的？從哪個管道？由什麼觸發？ |
| 二手/代答語氣 | 「聽說」「應該是」「我猜」「他大概想要」 | 這是他親口跟你確認過的，還是你自己的理解？標記起來，之後找他核對 |
| 數字沒有分母/基準 | 「119筆」「提升了」「當月畢業學員」 | 相對於什麼？現在的基準是多少？這個詞是自然月還是梯次？限定哪些範圍？ |
| 範圍自砍語氣 | 「先做⋯就好」「應該很難全部做」 | 這是業務上真的只需要這樣，還是你自己猜測開發成本？先告訴我不受限制的理想版本 |
| 解法滲入業務語言 | 「系統應該要排程掃描」「用 AI 判斷」 | 業務上要達成的結果是什麼？退回去問，不寫技術方案 |
| 集合代稱不清 | 「他們」「大家」「有人」 | 具體是哪些人、哪個角色？ |
| 「沒有」被輕易接受 | 「沒有正式指定 Goal Metric」「沒有例外」 | 這個角色是不是這次要追蹤/依賴他執行的人？「沒有」通常代表還沒被問到對的角度，不是真的沒有 |
| 沒被追問到期望 | 描述完一個痛點就停下、往下一題走 | 如果這個問題被理想解決，你希望它變成怎麼運作？單一規則/參數也適用，不用等到談整體範圍才問 |
| 待確認沒有時間點 | 「這個我不確定」「待後續確認」 | 大概什麼時候能確認？由誰去確認？ |

## 現況流程逐步拆解技巧（萃取姿態，Step 2 用）

對話裡出現的每一個步驟都要問到，不是聽完大概描述就結束：

1. **工具追問**：這一步用什麼工具/系統？要問到全名，不是縮寫或代號。
2. **動作追問**：實際做了什麼？「處理」「跟進」這種動詞太抽象，要問到「點開哪個畫面、看什麼欄位、輸入什麼、傳送什麼內容到哪個渠道」這種可想像的具體動作。
3. **份量追問**：這一步花多久、多常做一次、由誰做？
4. **本人/代答判斷**：這一步是這個人自己做的，還是別人（不在場的同事）做的？是別人做的就標記待確認＋負責人＋預計確認時間，不要一句「不清楚，待後續確認」帶過整個人的工作方式。
5. **責任歸屬追問**：現在有沒有人／哪個角色正式負責這件事？「有人在做但不是他的正式職責」本身常常就是痛點的一部分，要問出來、寫進痛點，不要漏掉。

**每個痛點都順手問一次期望，不要留到 Step 6 才一次問**：「如果這個問題被理想解決，你希望它變成怎麼運作？」現況問完就順手問。這裡蒐集到的答案，會是 Step 6「理想樣貌」的原始素材；也適用在單一規則/參數上（例如「這兩個時間點理想上應該是什麼時候？」），不是只能用在整體範圍層級。

## 目標精確度技巧（挑戰姿態，Step 3 用）

對每一位需求方追問到以下都有答案：

- 他個人/團隊要扛的目標是什麼？這個目標怎麼呼應上層目標？
- Goal Metric 是什麼？——一定要有公式（分子/分母）和目標值，不能只是「變好」「提升」「優化」。
- **公式裡的每個詞都要拆到只剩一種讀法**：像「當月畢業學員」這種詞看起來清楚，其實可能有好幾種讀法——是自然月還是這個梯次的畢業日？限定哪些班別？不能公式有分子分母就收手。
- **問清楚這個數字今天量不量得到**：「這個分子/分母，你們今天有什麼方式可以拿到實際數字？」如果指標依賴的歸因/追蹤機制根本不存在（例如要驗證「這個新客是不是從 OO 來的」卻沒有追蹤碼），這是指標本身的前提缺口，要記下來。
- 這個目標容不容易被誤會成更大的範圍？容易誤會就追問「這個目標不包含什麼」。
- **執行者角色不能輕易用「無」打發 Goal Metric**：如果這個角色是這次要追蹤/依賴他實際執行的人（不是單純受益者），對方卻說「沒有正式指定 Goal Metric」，追問一次「為什麼不用正式指定？」。
- 分辨本人回答 vs. 代答：追問「這是他親口跟你確認過的，還是你自己的理解？」在文件裡註明「（由 OO 代答，尚未經本人確認）」。

## 例外情況引導技巧（Step 5 用，至少換 2-3 種角度）

問完「有沒有例外？」得到「沒有/應該都一樣」時，**不要接受、不要就此收手**——這通常代表使用者當下沒被觸發記憶，不是真的沒有例外：

1. **類別提示法**——逐一用具體類別問：
   - 時間邊界：月初/月底、跨年跨月、假日、系統維護時段會不會不一樣？
   - 人員邊界：VIP、離職/停用帳號、代理人操作、身分重疊會不會不一樣？
   - 數量邊界：零筆、只有一筆、超過上限會怎樣？
   - 資料邊界：資料缺漏、重複、格式不對、跨系統對不起來會怎樣？
   - 狀態邊界：正在變狀態的當下（審核中、退款中、即將到期）會怎樣？
2. **過去事故回憶法**——「有沒有發生過因為這個流程沒考慮到，出過包、被客訴、或內部吵過架的狀況？」真實發生過的事故比憑空想像容易回憶，也更有說服力。
3. **搗蛋鬼提問法**——「如果有人想鑽這個規則的漏洞，會怎麼鑽？」
4. **逐一角色複查法**——回頭看 Step 4 列出的每個角色，各問一次「這個角色在這個情境裡，有沒有什麼不尋常的狀況？」不同角色的例外通常不一樣。

## 自我設限偵測（Step 6 用）

- **先整合 Step 2 蒐集到的各項期望，再問一次整體理想樣貌**：「先不考慮做起來要花多少時間，妳理想上希望這個機制運作成什麼樣子、覆蓋到哪裡？」
- **判斷是不是「順便夾帶」**：拿掉這個新加的項目，原本的痛點情境還是完整成立、而且是「另一群人/另一個場景」在卡關 → 那是夾帶，建議另開一份 BRD；同一個情境裡拆不開的一部分 → 才算自然延伸。
- **判斷是不是「需求方自我設限」**：範圍縮小的理由如果是「我猜這樣比較好做」而不是「業務上真的只影響這群人」，要拉回去問理想樣貌——這種縮小不該由需求方自己決定，範圍怎麼分期是 PM 的工作。
- **範圍描述不能寫成技術方案**：「改用系統自動排程取代人工 App script」是解法，改寫成業務結果。

## 待確認事項管理（貫穿全程）

「常常/很多/應該/大概」這類**主觀模糊詞**一律追問到有具體數字或案例為止，不能用「待確認」打發過去。但像「對接 PM 是誰」這類**客觀事實、當事人當下真的不知道**的缺口，才能標記「待確認」——不要為了填表逼使用者硬掰答案。每個「待確認」都要追問「大概什麼時候能確認、由誰去確認」，訪談結束前收進範本的「待確認事項一覽」表。

## 追問對照表（範例，不限於表列用詞）

| 使用者說 | 追問方向 |
|---|---|
| 「客服很常要處理這個」 | 「常」是多常？一天/一週幾次？每次花多久？ |
| 「幫我們加一個匯出按鈕」 | 這是要解決什麼問題？現在沒有這個功能，你們怎麼處理？卡在哪裡？ |
| 「這個很重要，要優先做」 | 不做的話，具體會發生什麼？有沒有時間點（稽核/合約/法規）？ |
| 「客戶反應不好用」 | 具體是哪個步驟？客戶原話是什麼？能不能給截圖或工單號？ |
| 「應該要……」「大概……」 | 有沒有實際發生過的案例？可以舉一個具體情境嗎？ |
| 「希望大家更有效率／目標是提升 XX」 | 這對應到哪個更大的部門/公司目標？可驗證的指標公式是什麼？除了你，還有誰也對這個結果負責？ |
| 「應該沒什麼特別例外／大概都一樣」 | 不要就此收手，換角度問：有沒有因為這個流程出過包、被客訴？如果有人想鑽這個規則的漏洞，會怎麼鑽？ |
| 「他應該是想要……」「我猜他是希望……」 | 這是他親口跟你確認過的，還是你自己的理解/猜測？標記起來，提醒之後找他核對 |

| 「當月畢業學員／本月新客／這批人」（指標公式裡的詞） | 這是指自然月還是這個梯次的畢業日？限定哪些班別/範圍？ |
| 「這個目前沒辦法追蹤／沒有工具可以驗證」 | 那這個數字你們打算怎麼算出來？這是指標本身的前提缺口 |
| 「先做 OOO 就好，其他之後再說」 | 這是業務上真的只需要 OOO，還是你自己猜測開發成本？先告訴我不受限制的理想版本 |
| （描述完一個痛點就停下） | 如果這個問題被理想解決，你希望它變成怎麼運作？ |

## 常見錯誤與修正

| ❌ 常見寫法 | ✅ 修正方向 |
|---|---|
| 「幫我們加一個一鍵匯出」 | 「業務代表每月手動整理報表要 20 分鐘，因為系統沒有批次匯出；需要能一次取得整月資料」 |
| 「客服很常抱怨這個流程」 | 「客服每天平均處理 15 次此類申請，每次要查 3 個系統約 8 分鐘，一個月約 40 工時」 |
| 「這個很重要要優先做」 | 「若 8/15 前不解決，下週五的客戶稽核會有法遵風險，因為……」 |
| 只寫 Happy Path | 至少補一個「如果……呢？」的例外情況 |
| 問「有沒有例外？」得到「沒有」就結案 | 換角度追問：有沒有出過包/被客訴？如果有人想鑽漏洞會怎麼鑽？逐一角色分別問一次 |
| 成功指標寫「變好用」 | 改寫成可驗證的數字或行為（如：處理時間從 8 分降到 2 分內） |
| 目標只問了提出需求的那一個人 | 追問還有誰也對結果負責，每個人各自問到目標與 Goal Metric |
| 目標沒有對應到公司/部門目標，也沒有指標公式 | 寫成：上層目標 → 這個人的目標 → Goal Metric（含公式） |
| 業務規則/範圍寫成技術方案 | 改寫成業務結果（如「系統要能可靠判斷是否已執行，不因時間差誤判」） |
| 需求方的目標其實是別人代答、猜的，卻寫得跟本人確認一樣篤定 | 標記「（由 OO 代答，尚未經本人確認）」 |
| 現況流程只寫步驟名稱，工具/縮寫沒解釋 | 每個工具/縮寫當場問清楚是什麼，流程拆到看得懂實際動作 |
| 別人的工作流程不清楚，一句「待後續確認」帶過整段 | 標記「待 OO 確認」＋預計確認時間 |
| 指標公式裡的詞彙有多種解讀 | 追問到只剩一種讀法：自然月/梯次、涵蓋哪些班別 |
| 指標依賴的歸因/追蹤機制其實不存在 | 記錄成指標的前提缺口，不能假裝指標已經完整 |
| 執行者角色的 Goal Metric 直接寫「無」就結案 | 追問一次「為什麼不用正式指定？」 |
| 需求方自己先把範圍砍小，理由是猜測開發成本 | 追問理想樣貌、不受限制的完整版本 |
| 「待確認」事項沒有時間點 | 每個待確認都問「大概什麼時候能確認、由誰確認」 |
| 只挖現況、沒問期望 | 每個痛點問完現況就順手問「理想上希望怎樣」 |
| 「有人在做這件事」但沒人正式負責，沒被寫進痛點 | 追問「這現在是誰的正式職責？沒有的話算誰在做？」 |

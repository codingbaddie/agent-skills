> **適用對象**：提出需求的業務/專業服務單位，交付給軟體 PM
> **目的**：讓 PM 不需要來回反覆確認，就能判斷「要不要做」「有多急」「大概怎麼做」

## 2. 需求方與商業目標（Goal Cascade）

> 一個需求常常不只一個人關心，而且每個人扛的目標可能不一樣。這裡要把「上層目標 → 各需求方自己的目標 → 可驗證的指標」層層對應寫清楚，PM 才能判斷這件事對誰有價值、優先滿足誰。**這節不能空，也不能只寫一個人。**

### 上層商業目標（這個需求要往哪個更大的目標貢獻）

> ❌ 「希望大家做事更有效率」
> ✅ 「健康管理部門 2026 進階課程營收 1000 萬」

|---|---|---|---|---|
|  |  |  |  |  |

> 範例：「助教／健管部」負責範圍是輔助課程運作，目標是「了解學員失聯原因、改善服務品質」，Goal Metric 是「失聯原因填寫率 80%（有填原因的人數 ÷ 失聯人數）」，不包含「挽回失聯的這個客人」——因為目標是找出原因改善流程，不是這次真的把人留下來。

> ⚠️ 公式裡的詞彙要拆到只剩一種讀法（例如「當月畢業學員」是自然月還是這個梯次的畢業日？限定哪些班別？），並確認分子/分母今天有沒有辦法實際量到——依賴的歸因/追蹤機制如果根本不存在，記成前提缺口，不要假裝指標已經完整。「無正式指定 Goal Metric」如果是要追蹤/依賴其實際執行的角色（不是單純受益者），要再想一次為什麼不用正式指定。

## 4. 業務規則與例外情況（用業務語言描述，不寫 UI/技術）

> 格式：如果 [情境]，則 [業務上應該發生的結果]
> 範例：如果客戶在合約到期前 30 天內申請退款，則需要主管簽核；超過 30 天則自動退款。
>
> ⚠️ 寫到「系統要排程掃描」「用 AI/關鍵字分析判斷」這類字眼時，代表已經在寫解法，不是業務規則了。退回去問「業務上要達成的結果是什麼」——例如把「系統每日定時掃描聊天記錄判斷是否執行」改寫成「系統要能可靠判斷是否已執行，不因資料時間差而誤判」。

[填寫]

### 例外與邊界情況（至少 2 個「如果……呢？」）

> ⚠️ 這節最容易漏。一次「有沒有例外？」通常問不出全部，「沒有特別例外」多半是還沒被問到能觸發記憶的角度，不是真的沒有。填之前換幾個角度逼自己想：
> - **時間邊界**：月初/月底、跨年跨月、假日、系統維護時段會不會不一樣？
> - **人員邊界**：VIP、離職/停用帳號、代理人操作會不會不一樣？
> - **數量邊界**：零筆、只有一筆、超過上限會怎樣？
> - **資料邊界**：資料缺漏、重複、跨系統對不起來會怎樣？
> - **狀態邊界**：正在變狀態的當下（審核中、退款中、即將到期）會怎樣？
> - **過去事故**：有沒有因為這個流程沒考慮到，出過包、被客訴、或內部吵過架？
> - 也對第 3 節列出的每個角色各想一次——不同角色的例外通常不一樣。

## 8. 提交前自我檢查（Self Check）

- [ ] 有沒有把「解法」寫成「問題」了？（例如寫「加一個按鈕」而不是「客服要花 X 分鐘手動做 Y」）
- [ ] 痛點有沒有數字或具體案例支撐？
- [ ] 現況流程有拆到動作層級（工具全名、實際動作、頻率/耗時、由誰做）嗎？每個痛點旁邊有沒有寫「理想上希望怎樣」？
- [ ] 「有人在做但沒人正式負責」這種落差，有沒有被寫進痛點？
- [ ] 有沒有至少一個例外情況？是不是換過角度想（時間/人員/數量/資料/狀態邊界、過去事故），不是問一次「有沒有例外」就收手？
- [ ] 每個需求方都有自己的目標和 Goal Metric（公式），不是只問了一個人、只寫一個籠統的目標？
- [ ] 每個需求方的目標都對得回第 2 節的上層商業目標？
- [ ] 容易被誤解的目標，有沒有寫清楚「不包含什麼」？
- [ ] 指標公式裡的詞彙是不是只剩一種讀法？分子/分母今天量不量得到，量不到的有沒有記成前提缺口？
- [ ] 第 2 節有沒有代答內容（幫不在場的人回答目標/使用情境/現況流程）沒標記來源？
- [ ] 第 4、5 節的業務規則/範圍描述，有沒有不小心寫成技術方案（如「系統排程」「AI 分析」）？
- [ ] 第 5 節的範圍縮小是業務理由，不是自己猜測開發成本？理想樣貌有沒有先記下來？
- [ ] 內部縮寫/系統代稱是否都列出來逐一檢查過，不是憑印象打勾？
- [ ] 待確認事項一覽表完整嗎？每一項都有預計確認時間與負責人？
- [ ] 沒參與過討論的 PM，看這份文件能不能懂？

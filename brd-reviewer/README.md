# brd-reviewer — PM 側的需求文件審查

收到業務單位交來的 BRD 之後，用這個 skill 審一遍，產出可以直接發給需求方的補件問題清單。

跟 `brd-writer` 是同一件事的兩端：

| | brd-writer | brd-reviewer |
|---|---|---|
| 誰用 | 業務／專業服務單位 | PM |
| 做什麼 | 訪談 → 產出 BRD | 收到 BRD → 挑缺口 → 產出問題清單 |
| 檢查角度 | 怎麼問才問得出來（技巧導向） | 文件長什麼樣代表沒問到（症狀導向） |
| 放哪裡 | 個人 repo ＋ `cofit-biz` plugin（全公司可裝） | 個人 repo（PM 自用） |

## 怎麼用

```
幫我看這份 BRD  <貼連結或路徑>
```

或者：「這份 BRD 還缺什麼」「幫我 review 一下這份需求文件」。

**同時給兩份以上**，它會額外比對有沒有撞到同一批人、同一份資料、同一段客戶旅程，並把「單方答不出來」的議題抽出來做成多方訪談議程。

## 產出什麼

**一份 BRD →** 一份補件問題清單。每一條有錨點原文（找得到位置）、可以直接發出去的問法、為什麼要問、以及 🔴🟡⚪ 分級。內建填答欄位，可以當訪談記錄用。

**多份 BRD →** 各自一份問題清單，加一份多方訪談議程。

## 兩個刻意的設計決定

**一、不要求需求方回頭改 BRD 原文。**
答案記在問題清單裡就好。要需求方去改文件等於要他做「跨章節對帳」——改了一個數字，別節的推論也要跟著改，那是收斂工作不是補資料工作。把散落資訊對帳成一致規格是 PRD 階段的事，做一次就好，不要需求方做一次、PM 再做一次。

原始 BRD 保持原樣反而有價值：它記錄了需求方原本的認知，本身就是訊號。

**二、分辨「需求方要補」跟「PM 自己要判斷」。**
開發成本、技術可行性、要不要分期、多份需求怎麼整合——這些是 PM 的工作，不會包裝成問題丟給需求方。

## 之後要做但現在不做：需求登記簿（registry）

### 要解決什麼

不同業務單位各自送需求進來，彼此稍微重疊卻沒人統整收斂，PM 收到的是一堆「看似不同」的需求。第一次遇到（2026-08，客保的兩份 BRD）是靠人把兩份文件並排讀才發現：兩份指派工作給同一批營養師、依賴同一份聊天室資料、負責同一條客戶旅程的前後段，而兩份文件都沒提到對方。

registry 就是一份清單，記錄**每一份 BRD 動到哪些人、用到哪些系統、在客戶旅程的哪一段、掛在哪個上層目標**。第 N 份進來時掃一眼就知道有沒有撞到，不用把前面幾份重讀一遍。

### 為什麼現在不做

**兩三份 BRD 用讀的就夠了。** 要到同時有四五份在跑、開始記不住誰跟誰撞到的時候，registry 才真的省事。現在建等於為還沒發生的問題先蓋基礎建設，而且會讓這個 skill 一開始就變複雜（維護清單、別名對照、放哪裡）。

**觸發時機**：當你發現自己在想「這份好像跟之前哪一份有關，但我要回去翻」——那就是該做了。

### 之後要做的話，已經想好的部分

**放哪裡**：`his-vault`（private repo），建議位置 `docs/alignment/BRD需求登記簿.md`，跟既有的 `成效追蹤-對照.md` 同一層（都是跨模組對照性質）。

⚠️ **不能放這個 repo**（`codingbaddie/agent-skills` 是 public），registry 會裝實際職稱、人數、內部系統名、部門營收目標。

**格式**：一份 BRD 一個區塊，記提出人／日期／連結／狀態，加上四個比對欄位（受影響角色含現有負載、資料源與系統、客戶歷程位置含上下游、上層商業目標）。

**四個欄位怎麼來**：BRD 範本第 8 節「跨需求碰撞面」（brd-writer v0.3.0 起）已經會產出這四項。舊版 BRD 沒有這節，由 skill 自己讀文件推導——推導規則見 `references/gap-checklist.md` 的 G 區。**推導不出來的標「文件未提及」，不准猜**，而推導失敗本身就是一條問題清單項目。

**別名問題（最關鍵的設計）**：「帶班營養師」和「營養師團隊(8人)」是同一批人，但字面完全不同，純字串比對一定失敗。所以流程是：

```
skill 掃 registry → 提出疑似交集 → PM 確認/否認
                                      ↓
                    確認結果寫進 his-vault 的 glossary（別名對照）
                                      ↓
                          下次同樣的詞自動判定，不用再問
```

`his-vault/docs/glossary.md` 開宗明義就寫「同一個詞在不同文件出現不同用法時，以本表為準」——它本來就是幹這個的。所以別名累積起來不只 brd-reviewer 用得到，做規劃、讀 context 時都用得到。這也是為什麼 registry 應該放 his-vault 而不是產品 repo。

**再自動一點的版本**：如果之後業務單位的 BRD 統一放某個 Drive 資料夾，可以掛排程每天掃一次新文件、自動跑分析與登記。這要等「BRD 一律放某個資料夾」變成流程規定才有意義——目前 BRD 產出不定時，等各單位開始更熱絡地寫再建立制度。

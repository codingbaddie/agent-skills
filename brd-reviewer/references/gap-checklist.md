# BRD 缺口檢查表（症狀導向）

給 `SKILL.md` 引用。每一項的寫法都是：**文件裡長什麼樣（症狀）→ 代表什麼沒被問到 → 要問什麼**。

跟 `brd-writer/references/elicitation-radar.md` 是同一件事的兩面，不是複製品——那邊是「訪談時怎麼問才問得出來」，這邊是「拿到成品，怎麼看出當初沒問到」。技巧導向 vs 症狀導向。

---

## A. 現況與痛點

| 症狀（文件裡長這樣） | 代表 | 要問什麼 |
|---|---|---|
| 有工時或比例，但沒有動作描述（「40% 在處理出貨確認」） | 現況沒拆到動作層級 | 用哪套系統、打開哪個畫面、看哪些欄位、做什麼操作、一筆多久 |
| 抽象動詞沒有對應的畫面／欄位／渠道（「處理」「跟進」「關心」「發送提醒」） | 同上 | 實際做了什麼？在哪個渠道、發什麼內容？ |
| 工具只寫縮寫或代號（「用 CHA 發」「POS」） | 沒問到全名 | 這是什麼的縮寫？完整名稱？公司內誰還在用？ |
| 別人的流程用一句「待確認」帶過整個人的工作方式 | 代答且沒追下去 | 請那個人自己用文字寫下流程；標記待確認＋負責人＋時間 |
| 「有人在做但那不是他的職責」 | ✅ 這其實寫對了 | 但要追問：現在誰正式負責？做完之後誰拿數據去要求改善？ |
| 痛點描述完就換下一段，沒有「理想上希望怎樣」 | 只挖現況沒問期望 | 如果這個問題被理想解決，希望它變成怎麼運作？ |
| 有數字但沒說怎麼算出來（「約 80% 的學員會流失一次機會」） | 數字沒有出處 | 分子分母各是什麼？資料期間？ |
| 現況替代做法寫「無」或「完全沒有」，但別處又說這個角色有在做某事 | 文件內部矛盾 | 那他現在實際上是怎麼做的？還是根本沒在做？ |

## B. 目標與指標（Goal Cascade）

| 症狀 | 代表 | 要問什麼 |
|---|---|---|
| Goal Cascade 只有提出人一個人 | 沒問「還有誰也對結果負責」 | 除了你，還有誰對這個結果負責、或會被影響？ |
| 指標寫「提升」「優化」「變好」，沒有公式 | 指標不可驗收 | 分子分母是什麼？目標值多少？現在多少？ |
| 公式裡的詞有多種讀法（「當月畢業學員」「首購人數」） | 沒逼到只剩一種讀法 | 自然月還是梯次？限定哪些範圍？cohort 還是當期？ |
| 指標依賴的歸因／追蹤機制沒有交代 | 前提缺口，上線後也算不出來 | 這個數字現在有什麼方式能實際拿到？有沒有推薦碼／關聯欄位？ |
| 執行者角色的 Goal Metric 寫「無」 | 「沒有」被輕易接受 | 這次要依賴他實際執行嗎？是的話為什麼不用正式指定？ |
| 上層目標是絕對數（每月 148 人），下層指標是比率（30%），但**沒有中間的基數** | Goal Cascade 在數學上斷掉 | 每月的分母大約幾人？這條路徑佔上層目標的比重多少、其餘從哪來？ |
| 容易被誤解成更大範圍的目標，沒寫「不包含什麼」 | 驗收時會爭議 | 這個目標不包含什麼？（例：預約 ≠ 到診 ≠ 訂閱） |
| 描述別人的目標卻寫得跟本人確認過一樣篤定 | 代答沒標記 | 這是他親口確認的還是你的理解？標記「（由 OO 代答）」 |
| 兩個需求方的指標看起來在算同一件事，但寫法不同 | 可能是同一個目標的兩種寫法 | 這兩個算的是同一群人嗎？數字對得起來嗎？ |

## C. 一致性（讀完全文才做得了，最容易被略過）

| 症狀 | 代表 | 要問什麼 |
|---|---|---|
| 同一件事的數字在不同節不一樣（一處 4-6 人工時、另一處 6-8 小時） | 前後矛盾 | 把兩處並排指出來：哪個才對？單位是同一種嗎？ |
| 一組百分比加不到 100% | 缺的狀態沒交代，而那常常是關鍵 | 剩下的那幾 % 是什麼狀態？ |
| 推算式（「154 人 × 1,500 元 ≈ 23 萬」） | **一定要自己算一次** | 算錯就直接指出；算對也要問每個參數的來源 |
| 兩個剛好相同的數字出現在不同語境（「1,200 位訂閱客戶」「每年 1,200 位首購」） | 可能同一個數字被誤用 | 這是巧合還是同一個數字用在兩個地方？ |
| Goal Metric 的動詞跟對應業務規則的動詞不同（指標算「完成回診」、規則觸發「未**預約**回診」） | 指標與規則錯位，驗收會爭議 | 這兩個是同一件事嗎？驗收以哪個為準？ |
| 有指標卻沒有任何規則會產生對應行為 | 指標沒有落地路徑 | 這個指標靠什麼達成？ |
| 有規則卻對不到任何指標 | 做了不知道有沒有效 | 這條規則做完之後，怎麼知道有沒有用？ |
| 角色出現在受影響對象或業務規則，卻不在 Goal Cascade | 執行者被漏掉 | 他是單純受益者，還是這次要依賴他執行的人？ |
| 人數在不同節不一致（一處 8 位、另一處 10 位） | 可能是資料時點不同，也可能是錯 | 是人員異動嗎？兩個數字的時點各是什麼時候？ |

## D. 業務規則與例外

| 症狀 | 代表 | 要問什麼 |
|---|---|---|
| 規則寫「系統每日定時掃描」「用 AI 分析判斷」「改用自動排程取代 App script」 | 解法滲入，不是業務規則 | 業務上要達成的結果是什麼？（順便問：可接受的誤判率多少？） |
| 被動語句沒有主詞（「發出警示通知」「會被提醒」） | 沒問到誰做、發到哪 | 誰發？哪個渠道？內容包含什麼？ |
| 「人工標記」「人工排查」當成角色寫 | 沒有正式負責人 | 誰有權標記／回查？多久一次？全查還抽查？ |
| 標記類規則沒有失效或解除規則 | 資料邊界例外沒問到 | 標記之後多久過期？誰能取消？看到過期標記會不會誤判？ |
| 例外少於 2 條，或只有 happy path | 例外沒問夠 | 用類別提示：時間／人員／數量／資料／狀態邊界，各問一次 |
| 例外有寫，但沒有涵蓋文件列出的每個角色 | 逐一角色複查沒做滿 | 對照受影響對象表，每個角色各問一次專屬例外 |
| 「原則上不會發生」「應該不會有」（請假、離職、資料缺漏） | 「沒有」被輕易接受 | 這件事真的不會發生嗎？發生時怎麼處理？會不會汙染指標？ |
| 某條例外把一部分人工作業保留下來 | 效益宣稱要打折 | 這種情況多久發生一次、每次多久？做完之後還剩多少人工工時？ |
| 沒有「過去事故」類的例外 | 最有說服力的一類沒問到 | 有沒有因為這個流程沒考慮到，出過包、被客訴、內部吵過架？ |

## E. 範圍界定

| 症狀 | 代表 | 要問什麼 |
|---|---|---|
| 沒有「理想樣貌」，直接列 In Scope | 沒問到不受限制的完整版 | 不考慮開發成本，這個機制理想上該長什麼樣、覆蓋到哪裡？ |
| 範圍縮小的理由是「先做一個比較快」「這樣應該比較好做」 | 需求方自我設限（分期是 PM 的工作） | 這是業務上真的只需要這樣，還是你猜測開發成本？ |
| Out of Scope 寫成技術方案 | 解法滲入 | 改寫成業務結果 |
| 某個痛點在 In Scope 裡找不到對應項 | 痛點與範圍沒有一一對應 | 這次做完之後這個痛點是完全沒被處理嗎？要寫明避免預期落差 |
| 加了一個項目，拿掉它原本的痛點情境仍然完整成立 | 順便夾帶，不是自然延伸 | 建議另開一份 BRD |
| 有相依需求但沒說明相依關係 | 成效上限沒講清楚 | 拿掉相依需求，這份還完整成立嗎？優先序要不要一起評估？ |

## F. 時程與待確認

| 症狀 | 代表 | 要問什麼 |
|---|---|---|
| 待確認事項沒有「預計確認時間」「由誰確認」 | PM 無法排進決策時程 | 每一項都補上時間與負責人 |
| 待確認散落各節，沒有收進一覽表 | 容易漏掉 | 統一整理成一張表 |
| 期望完成時間沒有理由，或理由是「越快越好」 | 沒問到 Why now | 為什麼是這個時間點？有什麼硬約束（稽核／合約／編制檢視／季度）？ |
| 「如果延後」的代價沒有量化 | 急迫性無法比較 | 延後一季具體損失多少？ |
| 文件註明的佐證資料時點距今很久 | 決策依據可能過期 | 有沒有更新的資料？結論會不會因此改變？ |

## G. 跨需求比對（只有拿到兩份以上才做）

先從每一份文件推導四項；**推導不出來的標「文件未提及」，不要猜**——推導失敗本身就是一條問題清單項目。

| 要推導的 | 從哪幾節聯集 |
|---|---|
| 受影響角色（含現有負載） | Goal Cascade ∪ 受影響對象 ∪ 業務規則的負責角色 |
| 資料源／系統 | 文件資訊的相關系統 ∪ 現況流程提到的工具 ∪ 規則依賴的資料 |
| 客戶歷程位置（含上下游） | 現況與痛點 ∪ 使用情境 |
| 上層商業目標 | Goal Cascade 的上層目標，直接引用 |

推導完之後比對：

| 交集在哪 | 嚴重度 | 產出什麼議題 |
|---|---|---|
| **受影響角色** | 🔴 最嚴重 | 工時從哪來、KPI 衝突以哪個為準、介面要不要整合 |
| **資料源／系統** | 🟡 | 是不是同一個技術能力？要不要當共用元件一起排 |
| **客戶歷程相鄰** | 🟡 | 交接點現在誰負責？兩份都沒涵蓋的話就是沒人負責 |
| **上層目標同一棵樹** | 🟡 | 兩個目標會不會互相拉扯？公司層級的優先序是什麼 |

⚠️ **名字幾乎一定對不起來。**「帶班營養師」和「營養師團隊(8人)」可能是同一批人，「聊天室」和「個人聊天室／CHA」可能是同一套系統。**不要用字面比對下結論**——提出疑似交集請 PM 確認，確認後才寫進報告。

## 分級規則

| 級別 | 判準 |
|---|---|
| 🔴 | **不補完，PM 的下一個決策就卡住**——例如效益數字自相矛盾（無法排優先序）、驗收指標有兩種讀法（無法定義完成）、現況不明（無法估效益） |
| 🟡 | 影響驗收品質或設計正確性，但不擋 scoping 開始 |
| ⚪ | 補充性質，補了更完整，不補也能往下走 |

分級看的是**「PM 的下一步卡不卡在這」**，不是問題本身大不大。一個小小的定義歧義如果會讓驗收無法進行，那就是 🔴。

## 常見的審查錯誤（自我檢查）

| ❌ 錯誤 | ✅ 修正 |
|---|---|
| 為了顯得認真而湊數挑毛病 | 找不到就說找不到；五條紮實的比二十條稀釋的有用 |
| 把 PM 的判斷包裝成問題丟給需求方（開發成本、要不要分期、多份需求怎麼整合） | 這些抽出來自己處理，不進問題清單 |
| 沒讀既有的 comment，重複問 PM 已經問過的 | 讀文件時一併讀 comment，重複的標記「已留過 comment」而不是刪掉（單一份完整清單比較好用） |
| 只挑文字表面問題（錯字、格式） | 只挑會影響決策的資訊缺口 |
| 推算式沒有自己算一次 | 一定要算——這是最容易抓到硬傷的一步 |
| 逐節挑完就交件，沒做一致性交叉核對 | 矛盾只有讀完全文才看得出來，而矛盾之處通常正好是最重要的論據 |
| 跨需求比對用字面比對角色名稱 | 提出疑似交集請 PM 確認 |
| 只列問題，沒講做得好的地方 | 最後一段一定要寫——需求方知道哪些做對了，下一份才會保持 |
| 要求需求方回頭改 BRD 原文 | 答案記在問題清單裡就好；對帳成一致規格是 PRD 階段的工作 |
